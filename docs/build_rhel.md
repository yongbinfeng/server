# Building Triton Inference Server on RHEL (unofficial)

RHEL-family is **not** an officially supported Triton target — build.py even
prints a warning to that effect. This document captures a working recipe for
building Triton on a RHEL-family host against a **stock** CUDA image, with the
`python`, `onnxruntime` (CPU or CUDA EP), and `pytorch` (CPU or CUDA) backends
(validated on AlmaLinux 9 with Rocky 9 containers, CUDA 13, Triton r26.06).

## Prebuilt image

A prebuilt image with all three backends (onnxruntime + pytorch GPU-capable) is
published on Docker Hub:

- https://hub.docker.com/r/yongbinfeng/tritonserver/tags

```bash
docker pull yongbinfeng/tritonserver:26.06_rhel
docker run --gpus all --rm -p 8000:8000 -p 8001:8001 -p 8002:8002 \
  -v /path/to/models:/models \
  yongbinfeng/tritonserver:26.06_rhel tritonserver --model-repository=/models
```

The build.py changes in this repo handle the buildbase and the final image.
The one piece build.py cannot fix is the ONNXRuntime build container, which is
generated by the upstream `onnxruntime_backend` repo — so that fix lives in a
small fork of that repo (step 2 below).

## 1. Host prerequisites

- Docker (with the containerd image store) and the invoking user in the
  `docker` group.
- **Put container storage on a large disk.** Moving Docker's `data-root` is
  NOT sufficient — Docker uses the containerd image store, so layers land in
  `/var/lib/containerd`. A full Triton build writes tens of GB; if that is on a
  small root filesystem it will fill up. Relocate containerd, e.g.:

  ```bash
  sudo systemctl stop docker docker.socket containerd
  sudo mv /var/lib/containerd /data/containerd
  sudo ln -s /data/containerd /var/lib/containerd
  sudo systemctl start containerd docker
  ```

- Internet access (pulls the CUDA base image and clones the r26.06 component
  and backend repos).

## 2. Fork onnxruntime_backend

The ONNXRuntime build container is generated by the upstream
`onnxruntime_backend` repo's `tools/gen_ort_dockerfile.py`, which build.py
cannot patch. Fork that repo (branch off **r26.06**, to match the rest of the
build) and adjust the RHEL branch of `gen_ort_dockerfile.py` so the container
provisions its own toolchain on a stock CUDA base:

- `--allowerasing` on the `dnf install` (curl vs curl-minimal).
- Add `patch` and `diffutils` (required by ORT's CMake FetchContent).
- Add `gcc-toolset-13-binutils` and use its `as` (2.40): the base binutils 2.35
  cannot encode the AVX-VNNI instruction (`vpdpbusds`) in ORT's MLAS kernels.
- Point `python3`/`pip3` at 3.12: ORT's `build.sh` runs `python3` with
  match-statements (needs Python >= 3.10); the RHEL base default is 3.9.

A reference implementation is on the `rhel-build-support` branch of
https://github.com/yongbinfeng/onnxruntime_backend.

## 3. Run the build

```bash
python3 ./build.py \
  --target-platform rhel \
  --no-container-interactive \
  --enable-gpu \
  --enable-logging --enable-stats --enable-metrics --enable-gpu-metrics \
  --endpoint http --endpoint grpc \
  --backend python \
  --backend onnxruntime:rhel-build-support \
  --backend-repo onnxruntime:https://github.com/yongbinfeng/onnxruntime_backend \
  --override-backend-cmake-arg onnxruntime:TRITON_ENABLE_GPU=OFF \
  --override-backend-cmake-arg onnxruntime:TRITON_ENABLE_ONNXRUNTIME_TENSORRT=OFF \
  --image base,nvidia/cuda:13.0.0-devel-rockylinux9
```

Flag notes:

- `--image base,nvidia/cuda:13.0.0-devel-rockylinux9` — required; a RHEL target
  has no default base image. CUDA 13 is needed because the Triton backend repo
  sets CUDA archs including the Blackwell family-conditional targets
  (`100f`/`120f`) that need nvcc >= 12.9.
- `--backend onnxruntime:<branch>` + `--backend-repo onnxruntime:<repo-url>`
  clone just the ONNXRuntime backend from your fork, without repointing every
  other repo (unlike the global `--github-organization`).
- The two `--override-backend-cmake-arg onnxruntime:...` flags build
  ONNXRuntime **CPU-only** (see the GPU section below to enable the CUDA EP).

The result is a `tritonserver:latest` image with the `python` and (CPU-only)
`onnxruntime` backends.

### GPU ONNXRuntime (CUDA execution provider)

To build ONNXRuntime with its CUDA execution provider instead of CPU-only:

- **Drop** `--override-backend-cmake-arg onnxruntime:TRITON_ENABLE_GPU=OFF`
  (leaving GPU enabled for the backend).
- **Keep** the `TRITON_ENABLE_ONNXRUNTIME_TENSORRT=OFF` override unless you
  also provision TensorRT.
- Pass the cuDNN location:
  `--extra-backend-cmake-arg onnxruntime:TRITON_BUILD_CUDNN_HOME=/usr`.
- Optionally restrict the CUDA architectures to speed up the build, e.g.
  `CUDA_ARCH_LIST="7.5" python3 ./build.py ...` (build.py forwards
  `CUDA_ARCH_LIST` into the builder). Omit it to build the full default set.

build.py installs cuDNN into both the ORT build container (via the fork's
`gen_ort_dockerfile.py`) and the final runtime image automatically when GPU is
enabled. Running the resulting image needs GPU access
(`nvidia-container-toolkit`, then `docker run --gpus all ...`); Triton then
places the ONNX model on `KIND_GPU` and runs it via the CUDA EP.

## 3b. PyTorch backend (CPU or GPU)

The PyTorch backend does not build libtorch from source -- it pulls a
"provider" docker image and `docker cp`s prebuilt libtorch libraries out of
it. Its RHEL path expects a **manylinux** layout, but the public
`nvcr.io/nvidia/pytorch` image is Ubuntu 24.04 (glibc 2.39) and will not load
on Rocky 9 (glibc 2.34). Instead, use a stock PyPI (manylinux) torch wheel.

The `pytorch_backend` fork (`rhel-build-support` branch of
https://github.com/yongbinfeng/pytorch_backend) makes the extraction
PyPI-friendly: it splits the CUDA-only libs out of `PT_LIBS` and gates them on
`TRITON_ENABLE_GPU`, empties the x86_64 `LIBTORCH_LIBS` (MKL redistributables
PyPI torch does not ship), makes the provider `docker pull` non-fatal (local
provider image), treats `libbackend_with_compiler`/`libaoti_custom_ops` as
optional (dropped in torch >= 2.9), and -- for GPU -- packages torch's own
bundled CUDA runtime libraries into the backend with an `$ORIGIN` rpath.

### CPU

```bash
docker build -t triton-pt-provider:cpu -f docker/Dockerfile.pt-provider .

python3 ./build.py --target-platform rhel --no-container-interactive --enable-gpu \
  --enable-logging --enable-stats --enable-metrics --enable-gpu-metrics \
  --endpoint http --endpoint grpc \
  --backend python \
  --backend pytorch:rhel-build-support \
  --backend-repo pytorch:https://github.com/yongbinfeng/pytorch_backend \
  --override-backend-cmake-arg pytorch:TRITON_ENABLE_GPU=OFF \
  --extra-backend-cmake-arg pytorch:TRITON_PYTORCH_NVSHMEM=OFF \
  --extra-backend-cmake-arg pytorch:TRITON_PYTORCH_ENABLE_TORCHVISION=OFF \
  --extra-backend-cmake-arg pytorch:TRITON_PYTORCH_ENABLE_TORCHTRT=OFF \
  --image base,nvidia/cuda:13.0.0-devel-rockylinux9 \
  --image pytorch,triton-pt-provider:cpu
```

### GPU (CUDA execution)

Use a **cu130** torch wheel so the bundled CUDA matches the CUDA 13 base
(`manylinux_2_28`, so it still runs on Rocky 9). Build the provider with GPU
build args and drop the `TRITON_ENABLE_GPU=OFF` override:

```bash
docker build -t triton-pt-provider:gpu \
  --build-arg TORCH_SPEC=torch==2.9.1+cu130 \
  --build-arg TORCH_INDEX=https://download.pytorch.org/whl/cu130 \
  -f docker/Dockerfile.pt-provider .

python3 ./build.py --target-platform rhel --no-container-interactive --enable-gpu \
  --enable-logging --enable-stats --enable-metrics --enable-gpu-metrics \
  --endpoint http --endpoint grpc \
  --backend python \
  --backend pytorch:rhel-build-support \
  --backend-repo pytorch:https://github.com/yongbinfeng/pytorch_backend \
  --extra-backend-cmake-arg pytorch:TRITON_PYTORCH_NVSHMEM=OFF \
  --extra-backend-cmake-arg pytorch:TRITON_PYTORCH_ENABLE_TORCHVISION=OFF \
  --extra-backend-cmake-arg pytorch:TRITON_PYTORCH_ENABLE_TORCHTRT=OFF \
  --image base,nvidia/cuda:13.0.0-devel-rockylinux9 \
  --image pytorch,triton-pt-provider:gpu
```

Run the resulting image with `docker run --gpus all ...`; Triton places the
model on `KIND_GPU` and libtorch runs it on the GPU via its bundled CUDA 13
runtime (packaged into the backend, `$ORIGIN`-rpath'd).

Notes:

- `--backend python` is included so the final image has a working `pip` (via
  the python backend's pyenv) for the tritonserver wheel install.
- This packages **stock PyPI torch** (e.g. 2.8 CPU / 2.9.1 cu130), not NVIDIA's
  `2.12.0a0.nv`. It loads and runs TorchScript models (forward-compatible) but
  is not bit-identical to NVIDIA's build.
- Iterate fast: build just the backend in the cached `tritonserver_buildbase`
  container (extract the pytorch cmake block from `build/cmake_build` and run it
  with the docker socket mounted) to avoid recompiling core every attempt.

## 4. Resuming after a final-stage failure

The compiled artifacts (core server + backends) are staged on the host under
`build/install`, and the final image is a standalone
`docker build -f build/Dockerfile .` that just `COPY`s them in. So if only the
final image step fails, you can fix its Dockerfile and rebuild just that image
without recompiling anything:

```bash
docker build -t tritonserver -f build/Dockerfile .
```

ONNXRuntime is likewise cached as the `tritonserver_onnxruntime` image once it
builds successfully, so subsequent full runs reuse it via `--cache-from`.

## What build.py itself carries

The in-repo build.py changes for the RHEL path (so a clone gets them):

- `--allowerasing` on the buildbase curl install (curl vs curl-minimal).
- Enable EPEL + CRB before the buildbase and final-image `-devel` installs.
- Use `dnf config-manager` instead of `yum-config-manager` (the latter breaks
  when python3 points at 3.12).
- `mkdir -p /opt/python` before the pyenv symlink.
- `PYTHON_BIN_PATH` uses the major.minor Python version (matches the pyenv
  binary name), not the full patch version.
- Add libffi/sqlite/bzip2/xz/zlib/ncurses `-devel` to the final-image Python
  install so pyenv builds a complete CPython (`_ctypes`, `_sqlite3`).
- Use `python3.12 -m pip` (not bare `pip3`) for the early final-image patchelf
  install: on a stock RHEL base `python3.12-pip` provides `pip3.12`, and a bare
  `pip3` only appears later via pyenv.
- Add `--backend-repo <backend>:<repo-url>` to clone a single backend from a
  fork without repointing every repo via `--github-organization`.
- Install cuDNN into the final runtime image for rhel + GPU + onnxruntime, so
  the ONNXRuntime CUDA execution provider can load `libcudnn` at inference.
- Forward the `CUDA_ARCH_LIST` env var into the builder container, so the ORT
  CUDA build can be restricted to specific architectures.
